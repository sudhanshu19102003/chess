# P2P Terminal Chess

A two-player terminal chess game written in Rust. Players connect directly (peer to peer), both clients validate every move, and a small server only introduces them. Hobby project, no deadlines.

Full design discussion (comments, diagram): https://claude.ai/artifact/2rTzNKjZThNAwaksKZN7xc. This file is the canonical summary for agents working in the repo. If the two disagree, ask the user. `README.md` is the player-facing guide (install, setup for online play, keys, fair-play rules, credits); keep it in step when behaviour, keys, flags or the install plan change.

### UI look and how it is drawn

The user asked for a polished **retro-game look with a sense of depth** (shadows, bevels, detailed pieces, not real 3D). Keep that bar when changing the UI.

- **One size.** The UI is designed for a single layout (the user's decision, to keep the code simple): 10-pixel squares, a 2-row clock strip above and below the board, and a 48-column panel, about 146x50 cells (`layout::needed`), centred in larger windows. Do not reintroduce size-adaptive layouts, piece tiers or fractional scaling; earlier attempts made pieces shrink and jump as the user zoomed, and the user asked for one size instead.
- **Clock strips.** Each player's small clock sits in a strip on their side of the board (`panel::strip`): name and turn on the left, the pieces they captured in the middle (sorted pawns first, then a material lead like `+5`), the clock on the right. Captured pieces are tiny 7x8 sprites on alternating board-coloured tiles in octant mode, and letters in half-block mode, where a 2-row strip is too short for any sprite. The side panel holds only the move history and key help; the user removed the big "CHESS" logo.
- Everything graphical is drawn into a pixel canvas (`canvas.rs`) and flushed with half-block characters, two square pixels per cell. Use the lower half block `▄` (fg = bottom pixel, bg = top), not `▀`: macOS Terminal takes the glyph from the font and draws it slightly low, and with `▀` that showed as stray lines above pieces and through the logo. Text (labels, history, help) is laid on top afterwards in the terminal's font (`render::Text`).
- **Pieces.** From the user's chosen sprite sheet: "Chess Asset 16bit pixel art" by gchoc, CC0, in `assets/pieces/` (see its README). The art is embedded as generated data in `src/sprite_sheet.rs`; regenerate with `cargo run --example import_sprites`, never edit by hand, and don't decode PNGs at runtime. In octant mode a square is 20 pixels and gets the sheet's 16x16 sprites at exactly 1x. In half-block mode it is 10 pixels and gets a hand-drawn 7x8 version in the sheet's palette (`pieces::small`, written in White's colours and recoloured for Black with the sheet's own tone pairing b/d/c to p/r/q). Pieces are hard-edged and never scaled; the user rejected blurry (anti-aliased) pieces, pieces that overhang their square, and Unicode chess glyphs.
- **Octant mode.** In terminals that draw Unicode 16 octants themselves, pieces, their shadows and the cursor are drawn on a canvas twice as fine (2x4 pixels per cell, `src/octant.rs`); cells without fine detail are emitted exactly as half blocks, so the board and panel are unchanged. A cell has only two colours, so `canvas::fit_cell` picks the best pair: a piece pixel may never take a board-only colour (light pieces otherwise vanish into light squares) and a board pixel takes a piece colour only at a cost. `pieces::render` nudges each sprite by up to a cell to the offset that loses least under that rule, simulated on both square colours. On by default only when `TERM_PROGRAM=ghostty`; `CHESS_PIXELS=octant|half` overrides and `g` toggles in game.
- **Zoom messages.** `layout::fit` decides what the window shows: too small for the layout gives a plain "zoom out" message instead of the board, at least 20% bigger than needed both ways gives a "zoom in" message (Enter plays at that size anyway, `App::play_anyway`), anything else gives the board (`panel::zoom_message`). There is deliberately no step counter: a terminal program cannot read the font size, and every attempt to count steps (guessing from pixel sizes, measuring from the first zoom, tracking possible font sizes) showed wrong or vanishing counts, so the user asked for these two plain messages instead. Do not bring a counter back.
- Truecolor by default. Without `COLORTERM=truecolor`, colours are mapped to xterm-256; `CHESS_COLORS=256|truecolor` overrides the detection.
- To see a change without a terminal: `cargo run --release --example snapshot -- <cols> <rows> out.png <scene>` (scenes listed under Status, plus `home|countdown|start|midgame|captures|check|mate|promotion`) renders a PNG; `docs/screenshot.png` (the README's) is the `midgame` scene at 146x50 with `CHESS_PIXELS=octant` (macOS fonts); set `CHESS_PIXELS=octant` for high-res pieces, since auto-detection would follow the shell's own terminal. `BENCH=60` also prints the time per frame. `tests/render.rs` renders many window sizes in both modes.

## Goals

- One-command launch: `curl -fsSL <url> | sh` installs a signed static binary.
- Keyboard-driven TUI: legal-move highlights, live updates, stepping through move history.
- Full rules: check, checkmate, castling, en passant, promotion, draw rules.
- No authoritative server. Both clients validate independently.

Non-goals: ratings, accounts, matchmaking, spectators, detecting engine assistance.

## Decisions already made

- **Language:** Rust. The user has a strong preference for it. Do not suggest switching to Go.
- **Chess rules:** write our own engine in a `chess-core` crate. `shakmaty` is allowed only in `[dev-dependencies]` as a test oracle, never in the shipped binary.
- **TUI:** `ratatui` + `crossterm`. The network runs in a `tokio` task and sends events to the UI loop over an `mpsc` channel.
- **Networking:** hand-written, no libp2p or iroh. TCP first, using simultaneous-open hole punching (`socket2` for `SO_REUSEADDR`/`SO_REUSEPORT` on a fixed local port). Add a UDP candidate later only if the measured direct-connection rate is poor.
- **Relay fallback:** TCP relay on port 443 that pairs two sockets by session ID and forwards bytes. Traffic is end-to-end encrypted, so the relay cannot read or alter moves.
- **Rendezvous server:** maps a short wordlist game code (like `7-crossword-pilot`) to peer addresses, single use, short TTL. It holds no game logic, and it only ever sees the number (the nameplate), never the words.
- **Crypto:** use existing crates (`spake2`, `snow`, `ed25519-dalek`), never hand-written primitives. The game code is the SPAKE2 password, so a malicious rendezvous server cannot sit in the middle. Crate choices were from memory: check versions and maintenance before depending on them.
- **SSH is not the transport.** Hosting the game over SSH (the terminal.shop model) makes the server the authority, which breaks the trust model.

## Verification protocol

Each client runs the same deterministic state machine and applies an opponent's move only if all checks pass. The first failure rejects the message and leaves state unchanged.

```
Move { game_id, ply, prev_hash, move (UCI), post_hash, sig (ed25519) }
```

1. Parse strictly; reject oversized or malformed messages.
2. `game_id` matches.
3. `sig` verifies against the opponent's signing key.
4. `ply` == local ply + 1.
5. Sender is the side to move.
6. `prev_hash` == local chain head.
7. `move` is in the legal moves of the current position.
8. Apply the move.
9. `post_hash` == hash of the resulting position.
10. Commit; `head = H(head, move, post_hash)`.

- The position hash covers pieces, side to move, castling rights, en passant square and both move counters.
- Draw and end-of-game rules (checkmate, stalemate, threefold repetition, 50-move, insufficient material) live in the state machine. A draw claim is accepted only if the receiver's own state agrees.
- On a post-hash mismatch after a legal move, halt and show both hashes. The handshake pins `engine_version`; clients with different versions refuse to play.
- The signed, hash-chained log is evidence a third party can verify offline.

Known limits: engine assistance and clock manipulation cannot be prevented without a trusted authority.

### Clocks

Clocks are in the first version. Built as described below (milestone 6), except that the lag check is now a per-move lag quota (Lichess-style, see `chess-tui` under Status) whose failure draws the game, instead of a per-game allowance that only warned.

- **Durations only.** The clients never compare wall-clock times, which can differ by seconds between machines. Each client times things with its own monotonic clock (`Instant`).
- **Time control.** Agreed in the handshake (base and increment, as in the offline presets) and bound into the genesis hash.
- **`think_ms` (u32) in every move message.** The sender's own measurement from receiving the opponent's move to sending this one (for White's first move, from the end of the start countdown). It is signed and chained: `head = H(head, move, think_ms, post_hash)`.
- **Agreed clock.** A player's remaining time is base, minus the sum of their `think_ms`, plus one increment per move they have made. It is computed from the log alone, so both clients and an offline verifier get the same figure, and network lag never counts against either player. The arithmetic lives in `chess-verify` next to `Chain`.
- **Out of time.** A move whose `think_ms` is more than the mover's remaining time is not played. The game ends on time: a loss for the mover, or a draw if the opponent has no mating material (the offline rule). Both clients reach this from the log.
- **Display.** While waiting, a client counts the opponent's clock down locally, then snaps to the agreed figure when the move arrives, usually a small jump back by about the network delay.
- **Lag check (local only).** For each opponent move the receiver works out the lag: observed gap minus `think_ms`. It is paid from a per-move lag quota (`online::LagQuota`, Lichess-style; constants under `chess-tui` in Status); a move the quota cannot pay draws the game. Ping/Pong messages (inside the Noise session, so authenticated; not signed, not logged) keep a round-trip estimate, which is displayed only: it plays no part in the check, because the opponent could inflate it by delaying Pongs. The check never changes the agreed clock. Nobody else can verify the receiver's observations, and letting them count would let a receiver overcharge.
- **Flag fall.** An honest client knows its own time exactly. When it runs out, the client sends a signed `Flag { game_id, ply, prev_hash, sig }` on its own turn, conceding on time. The receiver accepts it, since a player may always lose. If the opponent goes silent past their agreed time plus the quota they have left, the local client declares a win on time. This is not logged, and the silent side is not told.
- **Limit.** A dishonest player can still understate their thinking time by up to the lag quota. Within that bound, clock manipulation can't be prevented without a trusted authority. The 2026-10-24 timekeeping audit (https://claude.ai/artifact/57yypCjFkwGqo34Xdk5ZGW) lists the remaining gaps: disconnecting escapes a loss, the silent win is one-sided, no `TCP_NODELAY`, and an offline move in the frame after a flag fall still gets the increment.
- **Transport.** None of this depends on the transport: lag stays out of the agreed clock, so TCP's retransmit stalls cost nobody time. The TCP-or-UDP question is about connection rate only, and if UDP is ever added, use QUIC rather than plain UDP (moves need reliable, ordered delivery).

## Chess engine notes

Favour correctness over speed: `[Option<Piece>; 64]` board, pseudo-legal generation, then reject any move that leaves the mover's king in check.

Bugs to design against:
- En passant that exposes the mover's own king along a rank.
- Castling out of, through or into check; losing rights when a rook is captured on its home square.
- En passant target convention: count the square only when a legal capture exists, identically on both clients, because it affects the hash.
- Promotion to four pieces, including capture-promotions.
- Repetition across the whole game; 50-move reset on pawn moves and captures; every insufficient-material case.

Testing:
- **Perft** against known totals. Start position: 20, 400, 8,902, 197,281, 4,865,609 (depths 1 to 5). "Kiwipete" `r3k2r/p1ppqpb1/bn2pnp1/3PN3/1p2P3/2N2Q1p/PPPBBPPP/R3K2R w KQkq - 0 1`: 48, 2,039, 97,862, 4,085,603, 193,690,690. These figures are from memory: verify against the Chess Programming Wiki before relying on them.
- Differential test against `shakmaty` at every ply of random legal games.
- Property tests (apply then undo restores state; no legal move leaves own king in check), `proptest`.
- Fuzz the message parser (`cargo-fuzz`).
